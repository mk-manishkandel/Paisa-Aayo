# Publishing on Google Play

Everything the Play Console asks for, with the answers for Paisa Aayo. The store listing text and
images live in [`fastlane/metadata/android`](../../fastlane/metadata/android) (English `en-US` and
Nepali `ne-NP`) and are regenerated by `tools/brand/store_assets.py`.

## 0. Before you start

- **Developer account.** A personal account created after 13 Nov 2023 must run a **closed test
  with at least 12 testers for 14 days in a row** before it can apply for production. Plan for it:
  recruit shopkeepers and friends early. Organisation accounts (D-U-N-S number) skip this.
- **Signing.** Releases are signed with the key in `~/Documents/PaisaAayo-signing` (also in the
  macOS Keychain). See [Signing](#3-app-signing) before the first upload; the choice is permanent.

## 2. Upload the first build

1. Tag a release: `git tag v1.0.1 && git push origin v1.0.1`. GitHub Actions builds
   `PaisaAayo-1.0.1.aab` and attaches it, plus `PaisaAayo-1.0.1-mapping.txt`, to the GitHub Release.
2. Play Console → **Testing → Internal testing → Create release** → upload the `.aab`.
   The very first upload must be done by hand; the API can't create an app.
3. Upload the mapping file under **App bundle explorer → Downloads → ReTrace mapping file**
   (or let the workflow do it; see step 7).

## 3. App signing

Play re-signs what users download. Two options:

- **Recommended: use your own key as the app signing key.** On the first upload choose
  *Use a different key → Export and upload a key from Java keystore* and follow the PEPK steps
  with `release.jks` (alias `paisaaayo`). Then the APK on GitHub Releases and the Play version
  have the **same signature**, and users can switch between them without uninstalling.
- Let Google generate the key. Simpler, but the GitHub APK and the Play app become two
  incompatible installs; a user must uninstall one to install the other.

Either way, `release.jks` stays the **upload key**. Keep it backed up.

## 5. Data safety

The app has **no internet permission**, so nothing is collected or shared in Google's sense
(data processed only on the device is not "collected").

| Question | Answer |
|---|---|
| Does your app collect or share any of the required user data types? | **No** |
| Is all of the user data collected by your app encrypted in transit? | Not applicable (nothing is transmitted) |
| Do you provide a way for users to request that their data is deleted? | Yes: *Settings → Clear history*, or uninstall |

Mention on the listing / privacy policy: payment amounts, app names, reference numbers and times
are stored only on the device, for the period the user chooses (30/90/365 days).

## 6. Permissions and declarations

### Foreground service: `specialUse`

Play Console → App content → **Foreground service permissions** → *Special use*.

> **Description:** Paisa Aayo is a payment speaker for small shops. Its notification listener reads
> incoming payment notifications (eSewa, Khalti, Fonepay QR, bank SMS) and announces the amount
> aloud. A low-priority foreground notification keeps the listener alive so payments are announced
> immediately while the phone sits on the counter; the user can turn it off in Settings →
> Reliability → Persistent notification. Deferring the work would mean the shopkeeper isn't told about a payment while the
> customer is still at the counter.
>
> **User impact if interrupted:** payments are not announced; the shopkeeper may hand over goods
> without confirmation or ask the customer to pay twice.

A **video** is required: record the phone (a screen recording is fine) showing onboarding, the
"Listening for payments" notification, a test payment being announced, and the Settings switch
that turns the notification off. Upload it unlisted to YouTube and paste the link.

### Battery optimisation exemption (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`)

No form, but reviewers check it. Justification (use in *App access* notes if asked):

> The app's core function, announcing payments the moment they arrive, fails when the system or
> the phone maker's battery saver stops the notification listener. The exemption is requested
> once during setup with an explanation, can be skipped, and is never required to use the app.

### Notification access

No declaration form exists. The **prominent disclosure** is the "Allow notification access"
screen in onboarding: it states that all notifications are checked, what is kept, that nothing
leaves the phone, links the privacy policy, and the button reads *Agree and open settings*.

### Instructions for the reviewer (App access → Add instructions)

> No login is needed. On first launch choose a language and follow the setup. On the
> "Allow notification access" step tap *Agree and open settings* and enable Paisa Aayo. On the
> last step tap *Play test payment*: the app posts a sample "Rs 500 received" notification, reads
> it like a real payment and announces it. The same button is on the home screen ("Test sound").
> Real announcements need a payment notification from eSewa, Khalti, Fonepay or a Nepali bank.

## 7. Automatic uploads (optional)

After the first manual upload, the Release workflow can push each tagged build to the
**internal testing** track:

1. Google Cloud console → create a service account → create a JSON key.
2. Play Console → *Users and permissions* → invite the service account email; grant
   *Release apps to testing tracks* for Paisa Aayo.
3. GitHub → Settings → Secrets → Actions → add `PLAY_SERVICE_ACCOUNT_JSON` with the JSON contents.

Optional: to upload straight to your closed test instead of internal testing, add a repository
**variable** (Settings → Secrets and variables → Actions → *Variables*) named `PLAY_TRACK` with
the value `alpha` (closed testing, the default "Closed testing - Alpha" track), `beta` (open
testing) or `production`. For a custom closed track use its name exactly as shown in the Console.

The next `v*` tag uploads the `.aab`, mapping file and release notes from
`fastlane/metadata/android/whatsnew/`. Promote to closed/production in the Console.

## 8. Every release

1. Write release notes in `fastlane/metadata/android/whatsnew/whatsnew-en-US` and `-ne-NP`
   (≤ 500 characters each), and a copy in `*/changelogs/<versionCode>.txt`.
2. `git tag vX.Y.Z && git push origin vX.Y.Z` (versionCode = X·10000 + Y·100 + Z).
3. Check the GitHub Release, then roll out in the Play Console.
